# OctopusOn SEO Crawler (beta)

The CLI (`apps/snx-spider`) and desktop app (`apps/spider`) use the same crawl, storage, audit and export code. The desktop imports `@octopusseo/design`, like the Log Analyser, and sets `data-product="spider"`.

## Crawl a site

The **Schema & Rich Results** tool is separate from crawling and runs only after
**Test**. Paste a URL (optional JavaScript rendering), HTML or JSON-LD. A URL test
uses the existing crawl engine in bounded list mode with an in-memory sink; page
links are not followed and no crawl database or score update is created. Offline
source tests make no requests or execute scripts. The URL inspector's **Test
Schema** button only prefills the tool. Findings show the exact block/JSON pointer,
observed value, correction guidance and official source. Selected JSON-LD property
profiles are implemented; Microdata, RDFa, unknown profiles and contexts remain
explicitly unverified. This is a local preflight, not a Google Rich Results Test
verdict. See [ADR 0068](adr/0068-on-demand-schema-validation.md) for coverage.

For integrated checks, enable **Schema / zengin sonuç alanlarını tara ve puanla** in Configuration or the new/repeat crawl dialog. Required-property errors then appear in Issues and contribute to SEO Röntgeni and the overall score. The coverage panel separates inspected, scored, erroneous, recommended, missing and unverified URLs. Missing markup and recommended fields do not deduct points in this mode. Open **Tarama Schema raporu** in the URL inspector or the score remediation detail for saved field paths, observed values and correction examples. JavaScript mode validates the resulting DOM; failed or truncated documents stay unverified. Older crawls require a new opted-in crawl. See [ADR 0071](adr/0071-optional-crawl-schema-scoring.md).

Rule snapshot `2026-10-18.2` also checks supplied **WebPage** property shapes and **FAQPage** question/answer/text structure. Optional WebPage omissions do not create warnings. Page/FAQ structure advice never deducts score; Google retired FAQ rich results in May 2026, so no old eligibility requirements are imposed. Checked ListItem, Question and Answer components appear in the parent report rather than as unsupported features. Unresolved references and other unsupported types stay unverified. Old reports retain their recorded rule version and score; use an explicit URL retest or a new crawl for the new checks. See [ADR 0072](adr/0072-page-and-faq-schema-profiles.md).

Run `pnpm install` and `pnpm spider`. Enter an HTTP(S) URL, choose Spider or URL list, and start the crawl. Configuration controls the next crawl: user agent, robots policy, parallel requests, requests per second, URL/depth/time limits, scope patterns, resources, sitemaps and saved headers/HTML. Save the configuration to keep it across app restarts. The default desktop rate is 5 requests/second. A URL limit of 0 means unlimited; no licence limit is imposed.

The live **Crawl performance** block shows the running job's rendering mode, saved speed limits and starting-folder scope. Average HTTP time measures receipt of response headers; average page-operation time additionally includes assigned waits, body download, parsing and any JavaScript rendering. These means use successful page responses from the latest 100 operations, with the sample size shown, independently of feed filters. They are neither server-only/render-only timings nor a completion forecast. A request ceiling is not a guaranteed URL throughput.

**Stay in the starting folders** is an explicit choice in Configuration and new/repeat Spider dialogs. For a language section, use a trailing-slash seed such as `https://example.com/tr/`; without that slash the containing parent folder is used. Out-of-folder internal links remain recorded but their targets are not crawled. External checks follow their separate setting. The default remains unrestricted by starting folder; include/exclude rules and other limits still apply. A dialog change affects only its new crawl and cancellation preserves its source settings.

Concurrent HTTP requests must be between 1 and 64. Requests per second must be finite and nonnegative; 0 means unlimited, and positive fractional rates are supported. CLI and desktop starts both validate these settings before creating a crawl. Extremely small positive rates remain limited and cancellable instead of overflowing the scheduler or becoming unlimited. A browser resource whose request slot falls beyond its render deadline is not sent.

Sitemap discovery reads standard default/prefixed XML namespaces, URL sets, indexes and plain URL lists, with gzip detected from the content. Only direct sitemap loc/lastmod fields become discoveries; comments and extension URLs do not. XML text, CDATA and character references retain their intended values. Broken or truncated XML/HTTP responses, invalid UTF-8, unsupported DTDs, corrupt gzip and files above the 50 MiB uncompressed cap appear as sitemap errors and contribute no partial URLs. This does not perform full XSD validation. Existing saved crawls are not rewritten; repeat a crawl to collect corrected sitemap discoveries.

Sitemap files use HTTP/HTTPS fetch identities: fragments are removed before deduplication and before counting the sitemap limit. Repeated fragment references and cycles therefore cannot consume extra slots. Complete query strings and percent-encoded hashes remain distinct resources, even when page URL settings strip query parameters. Unsupported scheme hints are skipped without consuming the budget or creating HTTP errors; if no usable configured/robots sitemap exists, the usual /sitemap.xml discovery still runs. Original robots text is retained, including skipped hints and comments. This applies to both HTML and JavaScript crawls.

HTML URL resolution uses the first active base element with href, excluding inert template contents. A rejected data/javascript base falls back to the document address for relative links, canonical/hreflang annotations and resources; its resolved declaration remains available in URL facts. A later base does not replace the rejected first declaration. Fragment-only and empty a/area hyperlinks are retained when the effective HTTP(S) base points to a different document, including a different query string. Their fragments are removed for crawling and repeated references share one queue target. Same-document jumps remain omitted. Other non-HTTP bases do not become HTTP fallback addresses. Original HTML, rendered DOM and failed-render fallback share this extraction; existing archives require a new crawl to capture corrected observations.

Open **Explorer → Sitemap URLs** to inspect the original entry, its normalized crawl address, source sitemap, declared lastmod and observed status/indexability/depth. Search matches either address or source map; HTTP/indexability/finding filters and complete exports use the same results. Selecting a new entry opens its normalized page in the inspector. A crawl address identifies the potential queue target, not proof of a fetch: excluded, unsupported and unobserved entries keep unknown results. Several raw entries may refer to one fetched page; their original evidence remains separate while page findings count that page once. Page query rewriting never changes the sitemap file's source URL.

Site map files follow HTTP 301, 302, 303, 307 and 308 responses through the same unique-map queue, request-rate limit and Stop control. Each hop counts against the configured sitemap limit and keeps its original HTTP status; shared targets and cycles are fetched only once. Relative and cross-origin HTTP(S) targets are supported. The original Location header is saved even when storing headers is disabled; only literal fragments are removed from fetch targets, preserving query strings and encoded hashes. Missing/invalid Location, unsupported schemes and other HTTP statuses are reported as errors.

Open **Explorer → Sitemaps** to see the source status, redirect outcome, final address/status and parsed entry counts. Outcomes distinguish Complete, Failed, Loop and Unverified. A known failed destination or loop contributes the existing sitemap-error finding for its redirect sources. A target not fetched because of the sitemap limit or Stop remains unverified, without inventing an HTTP failure. A malformed final XML file can have HTTP 200 and still fail. A successfully parsed index is complete independently of failures in its child maps; the children retain their own results. Cycles have no final address, status or finite hop count. Optional columns and full exports include the original Location, next address and hop count; search matches source, next, Location and final address, while HTTP filters use the original response code.

New crawls use schema 9 for sitemap redirect observations and derived chains, retaining schema 8's normalized page identity beside the unchanged raw entry. Prepared schema 7 and 8 archives remain readable, exportable and comparable without being rewritten; their original schema/findings remain visible and no missing evidence is guessed. Archives below schema 7 or carrying a pending audit still follow the existing upgrade/refresh path. An upgraded legacy entry has no new identity unless it was recorded by a new crawl, so its report falls back to exact raw URL matching. Historical sitemap redirect errors cannot recover an unrecorded Location or destination. Repeat a crawl to collect the new observations.

Robots matching compares raw UTF-8 and percent-encoded paths consistently, including escaped unreserved ASCII and hex case. Reserved separators such as `/` and `%2F` remain distinct; path case stays significant. Equivalent rules have equal specificity and Allow wins ties. Reports keep each original rule and robots.txt text. UTF-8 BOMs and CR/LF/CRLF line endings are supported. HTTP pages and JavaScript resource requests share these decisions; ignore-but-report continues fetching while flagging blocked URLs.

Ignored robots.txt fields such as Crawl-delay, Host, Request-rate or custom extensions do not split shared User-agent groups. Actual Allow/Disallow records, including empty values, still separate the agent header from its rules. Sitemap records remain independent. This preserves common rules for every named crawler and keeps HTTP, JavaScript, AI access checks and Log Analyser reports consistent. These extension fields remain unsupported; request timing uses the configured crawl rate. Historical crawl observations are not rewritten.

HTTP X-Robots-Tag indexing directives apply only to the selected crawler: named Googlebot/Bingbot/OctopusOn SEO scopes require a matching token, while Chrome applies only unscoped rules. Separate header fields reset the scope and applicable restrictions merge conservatively. Original header text remains visible even when its rules do not apply. The same identity governs original HTML, rendered DOM, failed-render fallback and PDF/other HTTP resources. Historical archives retain their recorded flags; repeat a crawl to collect corrected Chrome observations.

A robots.txt response of HTTP 429 is an access problem, with its actual status retained, rather than a missing file that grants crawl permission. Like server/network failures, it blocks affected pages and in-scope browser resources in Respect mode for the current crawl; a blocked page has no invented HTTP response or request failure. Other 4xx responses retain their existing unrestricted robots behavior. Ignore-but-report fetches affected pages and keeps the rate-limit diagnostic; Ignore skips robots checks. The cache is separate for each scheme/host/port and does not automatically retry or resume when Retry-After elapses. Rerun after the server recovers. These are per-crawl application decisions, not a simulation of Google's historical cache and recovery schedule.

**Explorer → Robots.txt** shows translated access states beside the original HTTP code. Responses first encountered while checking a JavaScript resource are saved before the final audit, including when Stop preserves a partial crawl. They can produce robots findings without creating a fake page/resource row. Error bodies do not become robots rules or sitemap hints. Existing prepared archives and their measured outcomes are preserved; new crawls collect the corrected behavior.

Robots.txt follows up to five HTTP(S) redirects with status 301, 302, 303, 307 or 308, including cross-origin destinations. Relative targets resolve against the current hop; query strings and escaped `#` bytes are retained, while literal fragments are removed. Each URL in a chain is requested at most once. Other 3xx responses (including 304), invalid/non-HTTP targets, loops and exhausted chains remain conservatively Unavailable in this application. Respect blocks that original origin for the crawl, rather than interpreting a redirect/error body as permission. This conservative unresolved-chain policy differs from Google's documented unrestricted handling after excessive redirects. The HTTP column retains the last response actually received, including a redirect before a connection/chain failure, and never invents a 404. Successfully reached rules apply to the original origin; the destination origin keeps its own independent robots cache.

Crawls run in the background and save locally. Use the workspace selector to switch between completed crawls or active jobs; several jobs may run simultaneously. Pause prevents assigning more URLs; work already assigned to workers can finish. Stop cancels HTTP work still waiting for a request-rate slot, including pages/resources, external checks, sitemaps and well-known site files. Unsent work appears as cancelled in live activity and does not create a saved response or HTTP failure. Requests already being fetched finish under their HTTP timeout; their observations and any completed robots response are retained. Storage flush and auditing follow, so final-save time is separate from cancelling waits. A paused crawl can resume during this process session; restarting the app does not restore its frontier.

In **Saved crawls**, **Repeat as a new crawl** copies the saved plan into a review dialog. It preserves Spider/list mode, every seed URL, JavaScript/browser settings, request rate, limits, scope, resources and storage choices. Multiple Spider seeds remain separate URLs. The dialog allows URL, rendering-mode, worker-count, request-ceiling and browser-concurrency edits; the copied advanced settings can be inspected before starting. Unlike retrying only JS failures, a full repeat preserves the original URL/depth limits. Starting creates a separate crawl from its seed URLs and leaves the source and global configuration unchanged.

Saved `running` metadata is not proof of a live job. After a successful jobs snapshot, an unfinished record with no matching active job is labeled **No active job in this session** and offers the new-crawl workflow. The label only describes this app process; it does not determine another process's activity or rewrite saved status. While jobs are loading/unavailable, status remains unverified and saved-plan replay is disabled. Running/paused/stopping/finalizing jobs remain active even if their metadata was already finalized. Unfinished records retain the existing backend delete protection. The workspace selector includes date/status to distinguish repeated host names.

**Saved crawls** shows each archive's file size and a total for the visible library. Choose **Largest first** to find large records or **Refresh sizes** to measure again. Sizes include files in each crawl folder, including database journals and temporary files; the measurement does not open or change a database. Active crawls can change during measurement, and logical file size may differ from physical disk space recovered by deletion. Unavailable sizes remain unknown, sort last and are excluded from an explicitly labeled partial total. Measurements refresh while this screen is visible and a job is active, and after deletion. Deletion still requires the existing confirmation and remains blocked for active/unfinished crawls. Browser demo data has no native file sizes. This display does not measure development build caches.

Progress is available while crawling. The live view shows assigned URL operations and their elapsed time, plus the most recent 100 completions with HTTP status, analyzed title, JavaScript outcome and error details. Search and page/resource/external/error filters apply to this recent window; they do not query the entire crawl. Page, resource, robots, sitemap and site-file operations are distinguished. Browser subresource requests are not separate activity rows. HTTP/network errors, JavaScript failures and robots blocks have separate counters. Processing time includes rate-limit and rendering waits; HTTP time remains separate.

Activity updates are bounded snapshots delivered with counters a few times per second. Bodies, headers and link graphs are excluded; URL/title/error display strings are bounded. Full URL tables and findings open when the crawl and audit finish. The UI distinguishes browser startup, crawling, and final SEO analysis/saving. A stopped crawl is labeled stopped and retains partial results. Native close/quit requests are prevented while any job is running or finalizing, with a notification to stop and save first; force termination and OS failures remain outside this guard. Reloading the frontend can reconnect to an active job through its saved crawl ID, and revision numbers prevent older polling responses from overwriting newer events.

Memory in the sidebar is the native process's resident memory sampled every five seconds; it includes the database and desktop shell, but excludes separate Chrome processes. The UI shows a dash if the operating system cannot provide it.

HTTP status classes use bounded ranges consistently: 5xx findings cover only 500–599. Observed codes outside 200–599 appear as **Other HTTP**, including their non-indexable URL classification; an absent response remains distinct. Schema 7 updates those derived labels and recalculates saved findings when a finished crawl opens in the explorer. Stored HTTP observations and metadata are preserved, and no website requests are made during this update.

## Import a URL list

Choose **New crawl → URL list → Import URL file**. Local UTF-8 `.txt`, `.csv` and `.tsv` files are supported in the desktop and browser preview. TXT uses one absolute HTTP(S) URL per line, ignoring blank lines and `#` comments. CSV/TSV recognizes one Address, URL, URLs, Page, Landing page, Loc or Adres column; headerless input must contain one column. Comma, semicolon and tab separators, Excel `sep=` declarations, quoted delimiters, doubled quotes and quoted multiline headers/metadata are supported. CSV delimiter detection uses the complete logical header and recognized URL-column names, rather than punctuation frequency in other names. If multiple delimiters would select different URL columns, the file is rejected; specify the intended delimiter with a first line of `sep=,` or `sep=;`, or save as TSV. Inconsistent column counts or malformed quoting reject the entire file.

The preview reports every data record as a unique valid URL, duplicate or invalid entry. It shows at most five physical-line error examples and ten valid URLs. URL normalization preserves path/query meaning, serializes the host/default port and removes fragments before deduplication. Relative or scheme-less addresses, invalid percent escapes, whitespace/control characters and embedded credentials are invalid. Rejected credential text is not echoed into the preview.

**Replace URL draft** replaces the draft with valid imported URLs; **Append to URL draft** preserves existing URL order and removes overlaps. An invalid existing draft must be corrected before append, or explicitly replaced. File selection and preview never start a crawl or fetch imported addresses. Start is disabled until the import is applied or cancelled; a malformed file or cancelled preview preserves the existing draft. Starting uses the existing list-mode crawl pipeline and stored settings, including the configured HTML/JavaScript mode. Site-wide coverage remains limited to the list and followed redirects.

Spider and URL list keep separate URL drafts while the dialog is open. Switching modes preserves each draft and cancels any unapplied file preview. A single-address Spider draft initially uses the first nonempty seed; repeating a saved multi-seed plan still retains all seeds. Pasted lists accept CR, LF and CRLF line endings. Embedded ASCII control characters are rejected before URL parsing, preventing tabs or line breaks from silently joining addresses; percent-encoded path/query characters remain intact.

Each file is limited to 10 MiB, 100,000 data records and 512 columns. Oversized files are rejected without partial application; these are import limits, not a crawl licence limit. Save as UTF-8; compressed files, spreadsheets and XML are not accepted by this importer. It does not follow sitemap indexes or fetch remote list files. The CLI's existing `--list-file` workflow is unchanged. In the labeled browser preview, Start still produces sample crawl results; real site crawling requires the desktop app.

## Inspect results

HTML character decoding prefers a BOM, then a supported HTTP charset, then a bounded encoding prescan of the first 1024 bytes; UTF-8 remains the fallback. The byte prescan reads meta charset and pragma-gated http-equiv declarations, skipping comments and unrelated attributes without stopping at earlier legacy bytes. Unsupported labels fall through to later supported declarations. Quoted HTTP parameters, duplicate HTML attributes, UTF-16/x-user-defined meta compatibility and XML encoding signatures are handled. Original Content-Type evidence is preserved. This avoids corrupted Turkish text/URLs and false raw/DOM metadata differences; repeat historical crawls to collect corrected observations.

The overview shows actual counts, indexable internal HTML pages, response categories and prioritized findings. Findings are counted per rule and URL, so one URL can contribute to multiple findings. They are not a standardized SEO score.

Unused `<template>` content is excluded from page metadata, base URL selection, headings/anchor text, link/resource discovery and structured-data analysis, matching the [HTML template content model](https://html.spec.whatwg.org/multipage/scripting.html#the-template-element). JavaScript content cloned into the ordinary document is analyzed normally; nested inactive templates remain excluded. The same rule applies to original HTML and failed-render fallback. This does not add shadow-root serialization. Existing archives retain their original measurements; repeat a saved crawl to collect corrected observations.

Response counts classify every stored URL once: HTTP 2xx, 3xx, 4xx, 5xx, other HTTP codes, robots blocks without a response code, request failures without a code/block, and no recorded response. HTTP codes take precedence over diagnostic flags; a recorded 2xx does not establish successful JavaScript rendering. The final group does not assume why a response is missing. Unpersisted queue entries and browser subrequests are not counted. Select a nonempty overview group to open its URLs in **Response codes**. The response-outcome selector also includes robots/request/missing-response groups; literal search, sorting, pagination and filtered exports use the same database predicates. Error and robots columns explain null-status records. Existing crawls work without migration or recrawling.

The URL explorer uses a database query for each filter/sort/page change and renders only the visible rows. Each page contains at most 250 rows (the backend enforces a maximum of 1,000). Literal URL search, HTTP status class, indexability, affected-URL filters and column sorting run on the database. Select a URL to inspect stored facts, links, headers and optional HTML. The inspector offers separate internal/external incoming/outgoing tabs, previews at most 250 matching references and reports their full totals. **Explore incoming links** and **Explore outgoing links** open the complete selection in the Links explorer with pagination, sorting and export. A removable chip identifies the exact URL and direction. Search then applies to the other endpoint: referring URLs for incoming links, destination URLs for outgoing links. Without a URL scope, link search checks both endpoints. The Links tab's status filter refers to the destination's observed HTTP status; unknown statuses remain visible only with All selected. Selecting an outgoing scoped row inspects its destination; incoming rows inspect the referring page.

The inspector separates **Internal inlinks**, **External inlinks**, **Internal outlinks** and **External outlinks**, with full counts and 250-row previews that open in the complete Links explorer. Incoming classification follows the referring page; outgoing classification follows the destination. These counts include all recorded reference kinds. The URL table instead shows four separate hyperlink counts; column selection and complete exports retain them. External inlinks represent only sources recorded in this crawl. Link rows include both endpoint classes and destination request errors, and their distinct source/destination/record totals follow every filter over the full result set.

**Links to broken internal/external URLs** and **Links to redirects** now open exact matching link evidence: referring page, destination, HTTP status or request error, and anchor text. The finding count represents affected sources, so many sources may share one broken destination. Selecting a row opens that destination and its incoming references. Existing archives gain these read-time views without a migration or website request. Successful, blocked-only and unchecked destinations are not fabricated as broken links.

Issue details include a description and a suggested fix in English and Turkish. Exclusions are local preferences per crawl; they hide findings without deleting them. Issue exports cover the entire issues tab, including excluded findings. The URL explorer offers filtered exports as described below. Images and resource failures are reported on the page that references them.

Image discovery includes img src (and the existing lazy data-src fallback), valid img srcset candidates and preceding picture/source srcset alternatives. All declared media/type/size alternatives are listed, regardless of the browser viewport or selected image; Next.js optimizer query URLs and commas inside URLs remain intact. Duplicates are removed within one img while separate img occurrences retain their own alt text. Candidates inherit alt/lazy metadata; explicit source dimensions take precedence over img dimensions. Inert templates, invalid descriptors, non-HTTP URLs and unrelated/following sources are excluded. Enable image crawling to check response statuses and broken alternatives. With image crawling disabled, metadata remains available and response status stays unknown unless separately observed. JavaScript-created candidates use the rendered DOM; failed rendering uses source HTML. Repeat historical crawls to collect this expanded inventory.

HTML canonical fields use eligible link elements in the parsed document head. Body/template canonicals and canonical elements carrying `hreflang`, `lang`, `media` or `type` are ignored, following [Google's canonical guidance](https://developers.google.com/search/docs/crawling-indexing/consolidate-duplicate-urls). Repeated `canonical` relation tokens count as one element; separate valid elements remain separate declarations. This applies to original HTML and JavaScript DOM analysis, retaining the HTTP Link canonical fallback. Existing archives keep their original observations; repeat a saved crawl as a new crawl to capture corrected canonical facts.

HTTP `Link` canonical/alternate extraction respects quoted semicolons, commas and escaped characters. The first `rel` parameter wins; an explicit `anchor` must resolve to the fetched document for its annotations to apply. Header URLs resolve against the fetched URL, independently of an HTML base, following [RFC 8288](https://www.rfc-editor.org/rfc/rfc8288.html). The crawler discards malformed entries and non-HTTP(S) targets. This applies to HTML and non-HTML responses in either rendering mode, retaining header canonical fallback and DOM precedence. Existing archives keep their original observations; a new crawl collects the corrected facts.

Snippet limits retain the most restrictive valid `max-snippet` value across repeated declarations, HTTP headers and matching meta tags: zero prohibits a snippet, finite values use their minimum, and `-1` supplies no explicit limit. Later unlimited or malformed values cannot remove an existing restriction. `nosnippet` remains independent. This follows [Google's robots specifications](https://developers.google.com/search/docs/crawling-indexing/robots-meta-tag) and applies to new HTML and JavaScript analyses; existing archives retain their recorded values. A snippet restriction alone does not mark a page non-indexable.

The inspector's **Duplicate groups** tab shows up to five exact groups for the selected URL: stored title, meta description, first H1, first H2 and normalized visible-text hash. Counts include the selected URL and follow the existing audits' eligibility: internal, indexable 200 HTML pages with a nonempty field (positive word count and a stored fingerprint for content). Similar-content candidates remain a separate check. Field previews are limited to 512 Unicode characters, while equality uses the complete stored value. Normalized text includes navigation/footer content; a matching fingerprint is an audit signal rather than proof of plagiarism.

**List this group** opens all qualifying peers in the Internal explorer. The removable filter names the field and source URL, and the field being compared appears beside the URL. Literal URL search, status/indexability filters, sorting, pagination and filtered export continue to apply within the group. Navigating from a duplicate issue opens this inspector tab automatically. Changing explorer tabs or crawls clears the group; incoming/outgoing link navigation also clears it. Opening groups reads saved data without making site requests. Old crawls work immediately without a schema migration or recrawl.

Select **Redirect chain** in URL details to see ordered HTTP status codes and saved Location targets. The view reads stored records without contacting the site. It identifies HTTP errors, failed requests, robots blocks, cycles and automatic redirect responses without a usable saved Location. An unfetched destination is explicitly unknown. The preview contains at most 100 URL rows, including the starting URL and any repeated/unknown terminal URL; reaching this limit does not establish the final outcome. JavaScript navigation and meta refresh are separate from this HTTP trace. Opening a URL detail scrolls its panel into view.

Automatic page navigation and HTTP-chain findings use 301, 302, 303, 307 and 308. Other 3xx responses, including 300, 304, deprecated 305/306 and unknown codes, retain their actual status without following Location or parsing/rendering a document body. They have Other HTTP indexability. A blank/malformed Location produces no target; an explicit fragment-only self redirect still records a loop. HTTP 3xx response totals/filters include the entire family, while the automatic redirect count and redirect findings use only the five navigation codes. A chain ending at 304 has a recorded terminal response, not proof of fetched content or a missing-Location error. Historical erroneous targets do not extend a read-only trace. Prepared archive records/findings remain unchanged; recrawl to collect corrected page edges and audits. This crawler does not substitute a cached 200 body for 304.

The page/resource queue accepts HTTP/HTTPS only, including sitemap-only pages and redirect targets. A matching host does not make FTP, WebSocket, file or custom schemes internal web pages. Unsupported redirect targets remain in saved Location/link evidence and traces end unchecked; sitemap entries retain unknown response/indexability rather than invented request failures. They do not spend URL slots, even when external status checks are enabled. Genuine HTTP external checks still obey that setting. In new crawls, saved HTTP redirect destinations use the same fragment removal and configured query normalization as the fetched queue identity, keeping successful chains, loops and downstream error findings consistent. Original Location headers are retained when header storage is enabled. Existing archives keep their recorded targets and observations.

The redirect-to-error audit follows the observed chain through multiple redirects, so an early URL is flagged when a later target returns an HTTP error or a request fails. Cycle detection includes tails entering a loop. Shared chain suffixes are resolved once, without recursion. Saved findings are refreshed on opening an older crawl; raw records and crawl metadata remain intact. A pending-audit marker is cleared only in the successful findings transaction, so a failed or interrupted refresh is retried on the next open and preserves the previous findings.

Audit findings are computed in a database transaction after storage flushes. Crawl databases requiring an upgrade or a pending audit are prepared on opening; compatible, prepared schema 7 archives retain their original data and findings. The catalog contains 115 rule definitions, evaluated when their required data is available. Checks on unfetched targets are not inferred, and missing sitemap findings require an attempted sitemap fetch. `llms.txt` is reported missing only for a fetched 404/410 response. AI robot checks evaluate access to `/`, not all paths. Hreflang validation follows the language/region and return-link rules in [Google Search Central](https://developers.google.com/search/docs/specialty/international/localized-versions). Title and description widths are estimates. Response time measures time to headers, not Core Web Vitals.

The **Similar content** tab and `content-near-duplicate` finding identify candidates among internal, indexable 200 HTML pages with at least 200 visible words. Their 64-bit SimHash fingerprints must differ by at most 3 bits, and the shorter word count must be at least 80% of the longer. This is a heuristic, not a text-similarity percentage or search-engine decision. Visible text includes navigation/footer content. Equal normalized text hashes remain under the separate exact-duplicate rule. Failed JavaScript renders and truncated HTTP/DOM captures do not qualify. Successful JavaScript crawls use the analyzed DOM's fingerprint. Stored HTML is not required.

Each affected URL retains one observed example. Selecting a row opens that example in the inspector, including word counts and bit distance, with an action to inspect the other URL. This is neither an exhaustive pair list nor a cluster or nearest-match ranking. Both-endpoint literal search, sorting, pagination and CSV/JSON/XLSX export use the saved `content-matches` table. Opening examples makes no site requests. Schema 6 refreshes old crawls using their stored fingerprints and retains records/metadata. The algorithm groups exact text, indexes four 16-bit bands and stops after finding a witness, avoiding a stored pair cross product. Memory and saved matches grow linearly with pages; adversarial band collisions may still increase candidate work, and no million-URL benchmark is claimed.

The inspector's **URL findings** tab shows the selected URL's exact stored audit findings, ordered by priority, with explanations and corrections from the shared catalog. Its count includes excluded rules; **Show excluded** reveals them without changing exclusions or audit data. Unknown historical rule IDs remain visible. Empty results do not establish complete audit coverage or an error-free page. The inspector distinguishes URLs with no stored response/findings from older backends that cannot provide this field and reports any 1,000-row preview limit with the full total. **All URLs with this finding** opens the complete existing rule filter after clearing unrelated URL search, HTTP/indexability, link/duplicate/response scopes and pagination. Normal issue-filtered rows open the findings tab with that rule expanded; rendering and duplicate-specific workflows retain their dedicated comparisons. Inspection uses saved data and makes no site requests or database migrations.

## Exporting results

**Columns** in each explorer toolbar opens a searchable list of all fields returned for that tab. Choose optional fields, move them up/down, select all, clear optional fields or restore defaults. **Apply columns** saves the draft as a per-tab device preference; Cancel/Escape leaves the current layout unchanged. Layouts persist across crawl switches and app restarts without changing saved crawl data. URL identity fields stay visible. A duplicate comparison temporarily adds its relevant field; leaving the group removes that extra column unless it was explicitly selected. Hiding the active sort field also clears sorting and returns to the first page. Unsupported fields from older saved layouts are ignored; default columns are restored when none of a historical selection still exists.

In the URL explorer, **Export → Filtered results** writes every matching row using the current URL search, HTTP status/outcome, indexability, issue, exact duplicate group and incoming/outgoing link filters. The exported column order and sorting follow the displayed table. It includes all matching pages, rather than only the current 250-row page. A table that is loading, debouncing a search or showing previous query data must settle before filtered export is available. **Entire tab** retains the full-tab export with every column, including rows outside the selected group/link scope. Outside the explorer, exports continue to cover the entire tab.

**Clear all filters** appears whenever the explorer has an active search, HTTP status, indexability, issue, response group, link scope or duplicate group. It clears them together, cancels the pending search, returns to the first page and closes selected URL details, then focuses the search field. It keeps the selected crawl/tab, column layout, applicable sorting and saved issue-exclusion preferences. **Clear search** only empties the URL search, and each issue/link/duplicate chip removes only its own filter. Reset remains available when no rows match; row totals and filtered exports update through the same normal query.

CSV, JSON and XLSX share the same streaming query. Large exports are written by the backend without returning the complete dataset to the webview. The saved-row count is shown on completion, including empty filtered results. Exports finish into a temporary sibling file and replace the destination only after writing succeeds; failures preserve an existing report. Browser demo exports apply the same filters and projection for CSV/JSON; XLSX remains native-only.

## JavaScript rendering

When concurrent browser pages request the same eligible JavaScript or stylesheet before it is cached, the renderer can briefly wait for the existing download while continuing to handle browser events. A completed response is reused only if it passes the public immutable cache rules. Non-cacheable response headers, owner failure/cancellation and a bounded sharing deadline release the waiting page to its own normal policy-checked request. The wait deadline is at most two seconds and one quarter of the remaining active-page budget; each page can defer at most 128 resources and each crawl tracks at most 1,024 pending fills. This avoids repeated framework-chunk downloads during parallel startup while preserving independent HTML/API/private responses. Disabling the resource cache disables coordination too.

**Crawl speed** is available in Configuration and the new/repeat crawl dialog. Edit concurrent HTTP requests, the shared request ceiling (explicit 0 means unlimited; fractional rates are supported), and concurrent browser pages in JavaScript mode. The effective browser bound is the smaller of the HTTP worker and browser limits. Gentle selects 2 workers / 2 requests per second / 1 browser; Balanced selects 5 / 5 / 2; Fast selects 10 / 20 / 4. Profiles apply only when clicked. Existing/custom settings are preserved on opening; dialog cancellation leaves saved settings and source crawls unchanged. Profiles retain DOM waiting, timeouts, viewport, cache, coverage and robots policy. Clearing a number field is invalid and cannot silently enable unlimited requests. Faster profiles increase request traffic and browser memory use; actual URL throughput depends on the site. The dialog body scrolls while its header and Start/Cancel buttons remain visible.

Choose **JavaScript rendering** in New crawl or Configuration. Chrome, Chromium or Edge must be installed; the app discovers a browser automatically. Set the executable path in Configuration, use `--browser`, or set `OCTOPUSSEO_CHROME_PATH` if needed. The executable is the actual binary (on macOS, for example, `/Applications/Google Chrome.app/Contents/MacOS/Google Chrome`). Browser binaries are not downloaded or bundled.

A private headless browser is started per crawl and closed when it ends. Each URL uses a fresh context, so cookies, local storage and service workers do not carry over between URLs or access your personal browser profile. Default limits are two concurrent browser pages, a 30-second active render budget, a minimum 1,000 ms after DOMContentLoaded, and 500 ms with no active finite network requests. Browser slots are assigned in arrival order. Queued pages do not consume their execution budget and remain cancellable with Stop. Reported render time includes both queue and execution time, so it may exceed the active timeout. Wait time and concurrency are configurable. Requests from page scripts, styles and XHR use Chrome's normal network stack; the crawl's request-rate ceiling and internal robots.txt policy apply using the active page's deadline. Document navigations must also pass crawl scope rules. Robots checks for a newly encountered origin use the HTTP request timeout and can add latency to the render budget.

The main document is fetched once by the HTTP adapter and supplied to Chrome through DevTools interception. Its HTTP status, headers, response time, response size and header robots directives remain those of the original response, including redirects recorded without rendering. The browser executes scripts at the document's original URL/origin, with the configured user agent and language. HTTPS certificate checks, CSP and browser origin protections stay enabled. The resulting DOM drives titles, descriptions, headings, structured data, word counts, images and link discovery. JS-created hyperlinks enter the same scoped crawl queue, including robots and exclusion checks. Browser resource requests are not themselves URL-table rows unless a DOM reference also leads the crawl to them.

**Reuse static JavaScript and CSS** is enabled for new crawls. Shared, same-origin GET scripts/stylesheets with HTTP 200, explicit `public, immutable` and a fresh `max-age` are kept in a crawl-local memory cache (64 MiB, 2 MiB per body, 1,024 entries). This particularly helps sites sharing many framework chunks. Only network downloads consume request-rate slots; cached resources still pass robots, Stop and deadline checks. Cookies and page storage remain isolated. HTML, API/XHR/fetch, cross-origin or private/no-store/varying responses are not reused. Original HTTP resource status checks remain independent. Disable the option in Configuration or the new/repeat dialog, set `rendering.cache_resources` to false, or use `--no-render-cache` for diagnostics. The cache is discarded after the crawl and creates no disk files. Live-site gains depend on cache headers, server latency and settings.

The **Rendering** explorer tab/export compares original and rendered titles, descriptions, canonicals, noindex/nofollow directives, word counts and hyperlink counts; it also shows the URL after execution, render time, truncation and errors. Selecting a Rendering row opens the inspector's **Before / after JS** comparison, also available from other URL details. Canonical uses the first HTML canonical, falling back to the HTTP Link header; robots flags combine the response headers with the corresponding HTML directives. Missing metadata is distinct from an older crawl's unrecorded baseline. Failed rendering has no after-values in the comparison/table/export; the original-response fallback remains available in facts. Truncated DOM is explicitly marked incomplete. **Store HTML** keeps both representations: HTML source is the analyzed DOM and Original HTML is the server response. Metadata comparison does not require storing either HTML representation.

The high-priority `render-noindex-removed` finding identifies successful, untruncated internal HTML responses where the original effective noindex disappears after JavaScript. HTTP noindex that still applies after rendering does not trigger this finding. Failed renders, truncated DOM and unknown historical baselines are excluded. This follows [Google's guidance on robots meta tags](https://developers.google.com/search/docs/crawling-indexing/javascript/javascript-seo-basics#use-robots-meta-tags-carefully): an initial noindex can cause Google to skip rendering. The finding does not predict indexing, and the existing DOM-based indexability calculation remains unchanged. Schema 5 adds nullable original metadata; opening old crawls preserves their measured values and refreshes audits without fabricating a baseline. Recrawl to capture the new fields.

When a finished crawl has JavaScript failures, **Recrawl JS failures** in the Rendering tab prepares a new list crawl. All failure URLs are read in bounded pages ordered by address, including results beyond the first table page. Cancelled operations are excluded by the existing `render-error` rule. The dialog shows the editable URL list before starting; it retains the source crawl's browser, speed, robots and URL settings, enables JavaScript, and clears previous URL/depth limits. The source crawl is unchanged. Each attempt becomes a separate saved crawl.

HTTP `Link` hreflang annotations appear in the Hreflang explorer and exports alongside analyzed HTML/DOM annotations, even when saving headers and HTML is disabled. Identical language/target mappings are merged per source URL, comparing language codes without case; multiple language parameters and distinct targets remain separate. Header annotations also survive a failed-render fallback. Discovery settings control following targets, while reports retain observed annotations independently. Existing archives are not backfilled; repeat a saved plan to collect the corrected data.

HTML hreflang comes from active link elements directly inside the parsed head with alternate, hreflang and a resolvable href, excluding media-qualified annotations (including an empty media attribute). Body/template annotations and markup repaired into the body do not create alternate targets or satisfy return links. Repeated alternate relation tokens count once per element; separate declarations and invalid language codes remain available to existing validation. An alternate stylesheet keeps its independent CSS reference. Original HTML, rendered DOM and failed-render fallback share these rules; HTTP Link/PDF annotations retain their existing behavior. The Hreflang explorer explains eligibility. New crawls collect the corrected observations without changing prepared archives or adding rejected-element diagnostics.

List-crawl reports explain that site-wide relationships may be incomplete. The missing hreflang return-link check evaluates analyzed internal HTML targets and internal 200 PDFs in new crawls that record header-annotation coverage. Historical PDFs without that coverage, unparsed HTML status checks, redirects, failed/blocked responses, other non-HTML resources and external status checks cannot prove a missing annotation. PDF annotations also participate in self-reference, x-default, language-code, response and indexability checks. External annotations do not create site hreflang findings; unobserved targets remain unknown. This follows the bidirectional annotation requirement and PDF header method in [Google's localized-versions documentation](https://developers.google.com/search/docs/specialty/international/localized-versions); coverage guards are an application decision to avoid treating unknown results as failures.

Hreflang absence checks also consider a declared canonical only when the source and target are successfully analyzed, untruncated internal HTML; the target is indexable and self-canonical; declarations are unambiguous; page languages agree; the source annotations are all present in the canonical’s cluster; and the canonical has a language-specific self-reference. An exact return to the canonical then resolves a duplicate source return warning. Missing-self and optional x-default copies are resolved only with the corresponding canonical evidence. Conflicting, chained, missing, failed, noindex and unparsed canonical targets do not qualify. Parameters are never stripped, and alternate targets themselves are never silently canonicalized.

The Hreflang table/export keeps the observed mapping and shows source canonical, exact return (unknown for unchecked targets), verified canonical return context, numeric pagination candidate and observed text-hash equality separately. Numeric pagination parameters and different text hashes do not prove equivalent/different list items. Distinct pagination still needs canonical review; existing canonical findings are retained rather than adding duplicate hreflang penalties. Single-language content does not require nonexistent translations. These current report interpretations are read-only; SQL `audit_findings` and historical finding comparisons preserve the original observations.

A missing browser or launch failure stops the crawl with a clear error. A per-page rendering failure preserves the HTTP response, analyzes the original HTML and records a `render-error` finding. Rendered DOM exceeding the body-size cap (with a 64 MiB maximum) is flagged separately. Stop cancels pending browser waits and releases contexts. The renderer does not click controls, scroll to trigger infinite loading, log in, or serialize shadow roots/iframe documents into the parent DOM. Increase the settling time for scripts that intentionally load content later. Long-lived fetch requests can keep a page busy until its render timeout.

**Rendering viewport** offers Automatic, Desktop (1280×800), Mobile (390×844) and Custom. Automatic preserves the existing Googlebot Smartphone 412×915 mobile / other-agent 1280×800 desktop layouts. Custom width and height each accept 240–3840 CSS pixels, with a separate mobile-layout option. Layout does not change the selected HTTP/browser User-Agent or robots identity. Mobile layout honors viewport meta tags; page overflow and markup can affect actual inner dimensions. Pixel ratio stays one, without touch/hardware emulation. Saved plans, full repeats and JS-failure retries retain the setting; the overview shows the saved layout. Different viewports count as different settings in comparison coverage. Repeat a crawl to collect another layout's DOM and generated links; saved archives remain unchanged.

## Generate an XML sitemap

Open **Tools → XML sitemap** for a finished crawl. The tool reads its saved observations without requesting the website. It shows the first 100 eligible URLs, complete counts and a disjoint list of exclusion reasons. Each export contains one scheme/host/port origin. Choose another origin to generate that origin's sitemap; the origin with the most eligible URLs is selected initially.

Eligibility is deliberately conservative: internal, unblocked HTTP 200 HTML, recorded as indexable, with no request error, no observed noindex before or after JavaScript, no conflicting/non-self canonical and no truncated body/DOM. JavaScript crawls must have a successful saved rendering observation. Missing canonicals are allowed. Invalid URLs, credentials, fragments, malformed percent escapes, overlong URLs and ambiguous duplicate records are excluded. Scope/limit/list warnings describe incomplete coverage; absence from this sitemap does not prove a page is unindexable or absent from the website.

**Save XML** writes all eligible URLs, beyond the preview, with XML escaping and the sitemap namespace. **Save ZIP package** includes sitemap.xml as an index and numbered XML parts, automatically splitting at 50,000 URLs or 50 MiB per uncompressed document. When more than one document is required, use ZIP. Upload the extracted index and every part to the selected origin's root; index locations are generated for that root. Saving in the app only creates local files. Submission in Search Console or a robots.txt reference remains a separate publishing action.

No lastmod is inferred from capture timestamps; priority/changefreq are omitted. Output is atomic, requires the matching .xml/.zip extension and preserves an existing destination on failure. Archive access is read-only and rejects unfinished or pending-analysis records; open older finished crawls in the explorer first if their analysis needs updating. HTML storage is not required. The browser demo supports sample XML; ZIP is available in the desktop app.

## Current limits

- HTML mode remains the default. JavaScript mode requires an installed Chrome/Chromium/Edge. Custom rendering CSS is not yet available.
- Browser preview is a labeled demo. It does not fetch the entered site; native crawling avoids browser CORS restrictions. CSV/JSON demo exports contain sample data. XLSX requires the native app.
- Virtual rows and database pagination bound frontend memory. The crawl frontier and discovered-URL set still grow with the site; no million-URL benchmark has been completed.
- Scheduled crawling, self-hosted HTTP service and log/crawl joins remain future milestones. Crawl comparison matches exact URLs, tracked facts and archived finding pairs; URL rewriting/mapping and historical per-check pass/coverage logs are not included.
- An interrupted process is not resumable after restart. Keep completed/stopped crawls for later inspection.
- No login/session authentication yet. Fetching a URL does not guarantee it appears in a search engine's index.

## Overall SEO score

The overview shows a versioned 0–100 technical-health score and its largest rule deductions. Model v4 averages recorded internal URL scores: high/medium/low-priority findings deduct 20/7/2 each, with a 100-point cap per URL. UI-hidden findings remain included. Known Cloudflare email-protection and infrastructure patterns from the shared default URL exclusions are omitted from the score, including historical archives. Reference-based findings on pages linking to these addresses are rechecked against the remaining references, so a genuine broken link or empty anchor on the same page still counts. Arbitrary crawl exclusions are not retroactive scoring exceptions. Original stored findings are preserved; the UI displays excluded URL, reference and finding counts. Model v3 and later additionally remove proven canonical-cluster hreflang absence duplicates from current reports, remediation and scoring, including saved archives. It reports this exclusion count separately; canonical/pagination findings and unusable alternate targets still count.

**SEO Röntgeni** groups all 21 catalog branches into nine filterable systems.
